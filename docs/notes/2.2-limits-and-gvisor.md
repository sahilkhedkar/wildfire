# Batch 2.2: Limits and gVisor Configuration

## Built

- Typed sandbox limits for CPU, memory, swap, PIDs, disk quota, and maximum runtime.
- Docker `HostConfig` values for CPU, memory, swap, PID, and storage limits.
- Explicit runtime selection between `runc` and `runsc`.
- Wall-clock deadline returned with the sandbox handle for the upcoming manager/reaper implementation.
- Validation that rejects non-positive limits, non-integer PID limits, and swap below memory.

## Defaults

- 1 CPU
- 512 MiB memory
- 512 MiB memory plus swap ceiling
- 128 processes
- 2 GiB storage quota
- 15-minute maximum runtime
- `runc` runtime by default

## Environment note

The local Docker daemon currently exposes `runc` only; `runsc` is not installed. The client accepts `runtime: "runsc"` and emits the correct Docker configuration, but actual gVisor execution requires installing and registering gVisor with Docker on the host.

## Honest limitation

The returned deadline is policy data until the sandbox manager enforces it by stopping and removing expired containers. That lifecycle enforcement belongs to the next sandbox manager batch.
