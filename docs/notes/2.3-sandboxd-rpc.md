# Batch 2.3: sandboxd and RPC

## Built

- In-sandbox `sandboxd` HTTP server with `/healthz` readiness endpoint.
- Authenticated `POST /rpc` method dispatch using Bearer tokens.
- Constant-time token comparison using SHA-256 digests and `timingSafeEqual`.
- Injectable method handlers for the later file and command tools.
- Worker-side readiness polling with bounded attempts and delay.
- Tests for health, unauthorized access, authenticated RPC, and unavailable-daemon timeout.

## Decisions

- HTTP is the initial RPC transport because it works over Docker port forwarding and can later be replaced by a Unix socket or vsock without changing handler contracts.
- Health is intentionally unauthenticated so the sandbox manager can perform readiness checks without exposing tool access.
- RPC methods are injected rather than implemented in this batch; Batch 2.4 will place the Path Guard and file tools behind this boundary.

## Honest limitation

The current token is a per-daemon shared secret carried in an HTTP Bearer header. The Docker client and sandbox network policy still need to ensure that only the trusted worker can reach this endpoint; the RPC server alone is not a complete tenant isolation boundary.
