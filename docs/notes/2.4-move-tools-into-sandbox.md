# Batch 2.4: Move Tools Into sandboxd

## Built

- `sandboxd` now owns `read_file`, `write_file`, and `list_dir` implementations.
- The sandbox-local methods instantiate and call `TypeScriptPathGuard` before filesystem access.
- `SandboxdClient` provides authenticated RPC calls for the trusted worker side.
- The agent accepts a remote tool transport and can run without touching the worker filesystem.
- End-to-end tests cover sandboxd server, RPC client, file operations, and traversal denial.

## Decisions

- The agent depends on a structural `AgentToolTransport` interface rather than importing sandboxd internals.
- Local tools remain the default for the Phase 0 demo; supplying `toolTransport` switches the same loop to sandbox RPC.
- The sandboxd server returns tool errors through the authenticated RPC boundary, keeping filesystem decisions inside the sandbox process.

## Verification

The integration test starts sandboxd with a temporary workspace, performs write/read/list through `SandboxdClient`, and confirms `../outside.txt` is rejected by the sandbox-local Path Guard.

## Honest limitation

The Docker sandbox manager does not yet provision sandboxd or pass a real container endpoint into the CLI. This batch establishes and tests the boundary; the lifecycle manager wiring belongs to the next sandbox batch.
