# Batch 0.3: Agent Loop and First Tools

## Built

- Agent loop that sends task context to an `LLMProvider`, parses structured JSON tool calls, executes tools, and feeds results back into the conversation.
- Initial tools: `read_file`, `write_file`, and `list_dir`.
- Zod validation for tool names and arguments.
- Step and reported-token budgets with structured termination statuses.
- Local workspace path confinement for relative traversal attempts.
- Deterministic tests proving file creation, reading, listing, traversal rejection, and budget enforcement.

## Decisions

- Tool calls use a small JSON envelope in assistant text: `{ "tool": "...", "arguments": { ... } }`. This keeps the agent independent from one provider's native tool-call format while the LLM gateway is still small.
- Tool execution is behind a local map so the later sandbox RPC can replace filesystem implementations without changing the loop.
- Tool results are returned as user messages for now because the shared LLM message contract currently supports system, user, and assistant roles only.

## Honest limitation

The initial path check prevents normalized `..` traversal but does not yet resolve symlinks or close TOCTOU races. Those cases belong to Phase 1's Path Guard and the later sandbox boundary.

## Learned

The agent loop is primarily orchestration: provider responses, validated tool arguments, tool results, and budgets form explicit state. Keeping those boundaries typed makes the filesystem implementation replaceable.
